# Security audit — 2026-09-05

Audit of Phone Diagnostic Tool at commit `24c529e` (v1.1.2 shipped).

Findings below were verified against the **published v1.1.2 APK**, downloaded
from the GitHub Release and inspected, rather than inferred from the build
files. Where something is stated as present in the binary, it was observed
there.

---

## Finding 1 — The published APK is the debug build (High)

`.github/workflows/release.yml` attaches `app/build/outputs/apk/**debug**/app-debug.apk`.

Three consequences follow, all confirmed in the shipped binary.

### 1a. The app is debuggable

The `debuggable` attribute is present in the shipped manifest's string pool.
AGP omits that attribute entirely for release builds, so its presence is
meaningful rather than incidental.

With USB debugging enabled on the device, `run-as` gives a connected host full
read access to the app's private data directory — the rotating diagnostic log,
the 24-hour metric history, and preferences.

### 1b. The signing key is published in this repository

`keystore/debug.keystore.b64` decodes to a keystore containing a real
`PrivateKeyEntry`, not merely a certificate. Its password is `android`, stated
in plaintext in `app/build.gradle.kts`.

```
Owner:  CN=Android Debug, O=Android, C=US
SHA256: 0A:A4:46:AD:96:D5:15:2A:53:5A:80:F1:C0:70:C8:58:67:C6:10:42:16:33:33:46:97:DE:FA:F9:10:3F:96:28
```

Anyone can therefore produce an APK bearing this exact certificate. Android
treats a same-signature APK as an **update**: it installs over an existing
install, retains that install's data, and inherits permissions the user has
already granted — here that means **Usage Access and `QUERY_ALL_PACKAGES`**,
which is the permission set that matters most for this app.

This is the finding with real consequences. The other two are hygiene.

### 1c. Debug tooling ships to users

`androidx.compose.ui.tooling.PreviewActivity` appears in the shipped manifest,
and `ui-tooling`, `ui-tooling-data` and `ui-test-manifest` are all present in
the APK. Nothing is minified.

Result: **16.9 MB shipped, against 1.2 MB for the release variant** — a 14x
download for no benefit.

---

## What the audit found to be sound

Checked deliberately, and clean:

- **No hardware identifiers anywhere.** No IMEI, serial, `ANDROID_ID`, or MAC
  address is read by any code path.
- **One outbound endpoint**, opt-in via Settings: a TCP connect to `8.8.8.8:53`
  for latency timing. No payload is sent.
- **The shareable report contains no SSID, IP addresses, DNS servers, or
  carrier details.** Its NETWORK section carries only connection state, type,
  latency, link bandwidth, validated and metered flags. SSID is displayed
  on-screen only, and the platform redacts it because the app requests no
  location permission.
- Cloud backup and device transfer are excluded for every domain.
- Only `MainActivity` is exported. The monitor service is not exported.
- Both `PendingIntent`s use `FLAG_IMMUTABLE`.
- FileProvider is scoped to `cache/reports/` alone, is not exported, and shares
  go through `createChooser` with `FLAG_GRANT_READ_URI_PERMISSION`.
- Dependencies are current; none are known-vulnerable.

Minor: an exported report remains in `cacheDir/reports/` after sharing until
the next share clears the directory. App-private, low risk.

## Remediation options

### Option A — ship the release variant, same key (no user disruption)

Publish `app-release.apk` signed with the existing committed keystore rather
than `app-debug.apk`. Removes 1a and 1c. Because the certificate is unchanged,
existing installs upgrade normally.

Does **not** address 1b, but is strictly better than the status quo and needs
no new secrets.

Caveat: this puts R8 and resource shrinking in the shipping path for the first
time. The release variant has been compiled in CI all along, so it builds
clean, but it has never been *run*. Install and exercise the release APK before
cutting a release from it.

### Option B — a real release keystore (addresses 1b)

`app/build.gradle.kts` and the build workflow are already wired for this: they
read `RELEASE_STORE_FILE`, `RELEASE_STORE_PASSWORD`, `RELEASE_KEY_ALIAS` and
`RELEASE_KEY_PASSWORD`, and fall back gracefully when unset. See
[DISTRIBUTION.md](DISTRIBUTION.md) for the generation steps and the four
GitHub secrets to add.

The key must be generated by a human on their own machine and never pasted into
a chat transcript or CI log. Note that a new certificate means existing users
must uninstall before installing — Android will not accept it as an update.
